## 1. 结论摘要

### 1.1 三个正面结论

**① 亲和倾斜真实存在，且是稳定的结构性特征。**
prefill 侧 pod 间负载不均是**同负载下随机分配的 3.73 倍**（7 天中位，日间波动 3.31~4.46），99% 的时间窗超出随机分布 P95。这个倍数在所有负载档、所有小时、工作日与周末均稳定（§4）。

**② 缓存价值随上下文规模急剧放大，这是 P2P 的核心经济依据。**
在同等 prompt 规模下比较高命中（>90%）与低命中（<50%）请求的 e2e：

| prompt 规模 | 低命中 P50 | 高命中 P50 | 倍数 |
|---|---|---|---|
| 20k~60k | 3.13s | 0.59s | **5.3×** |
| 60k~120k | 7.14s | 0.80s | **8.9×** |
| 120k~300k | 13.62s | 1.21s | **11.3×** |
| >300k | 31.58s | 2.08s | **15.2×** |

该客户 prompt 中位 69831 token、P90 161788 —— **正落在缓存价值 9~11 倍的区间**。丢失缓存的代价随规模放大，这比简版引用的"冷热 pod 34 秒"更严谨（后者是小窗口偶发值，见 §4.4）。

**③ 负载预测已达可用水平，可交付。**
集群级 60 分钟 R²=0.827、倾斜告警 AUC=0.899、Top-K 预热选点全档位优于基线（§8）。

### 1.2 两个必须传达给合作方的判断

**① 现有 P2P 触发条件在当前状态下基本不会生效。**
排队只在高负载时段的尾部出现（全期 P90 仅 19ms，P99 达 11.1s，>1s 的请求占 2.6%）。若"负载差达标"依赖排队指标，98% 的时间不会触发。建议改用倾斜度（§5.2）。

**② 我们原方案的价值函数会加剧合作方要解决的问题，已修正为双边形式**（§7）。

### 1.3 一个坦率的局限

会话重建质量有限（Recall 0.067），依赖它的两个建模任务（会话延续 P、复用潜力 R̂）标签噪声很大。根因是日志无 block hash。**接入 KV Events 是最高优先级的外部依赖**（§9）。

## 2. 问题背景与合作方诉求

### 2.1 合作方在做什么

SGLang + Mooncake 的 P2P KV Transfer：

- **Gateway (Rust)**：订阅 worker ZMQ KV Events，用 block hash 维护全局「前缀 → worker/DP-rank/介质」HashTree；`P2pCacheAwareSelector` 选最长命中 source（需满足命中率>阈值、跨节点、**负载差达标**）；`P2pNodeGate` 做 source+target 双节点原子准入。
- **Worker 控制面**：每次 transfer 是异步状态机（PROBING→…→CONSENSUS→COMMIT），communicator 单飞 + pair gate。
- **数据面**：`DEVICE`（GPU KV 直传）/ `HICACHE_DIRECT`（host buffer 直传）。
- **失败语义**：fallback / quiesced / quarantined / cache integrity error(fail-stop)。原则是 P2P 失败不影响正常推理。

### 2.2 他们要解决的死锁

```
某类对话（同 system prompt 模板）落到某个 pod
        ↓
该 pod 缓存了这类前缀，命中率高
        ↓
cache-aware 选点倾向于把同类请求继续送给它
        ↓
该 pod 更热、缓存更全 → 吸引力更强  ⟲ 回到第二步
```

而简单把请求分给空闲 pod 要付出代价：空闲 pod 无缓存，每次全量 prefill（代价见 §1.1-②）。

**P2P 提供第三条路：先把 KV 搬到空闲 pod，再把请求路由过去。**

### 2.3 他们自述的缺口

> `P2pCacheAwareSelector` 是保守选点，只用前缀深度 + 负载阈值，无带宽/剩余计算模型，也无"哪个会话更可能延续/复用"的信号。

我们要补的就是这部分 —— 但方向需要修正（§7）。

## 3. 数据源：形态、坑、取数方案

### 3.1 定位

| 项 | 值 |
|---|---|
| 地域 | `ap-beijing` |
| 日志集 | `HAI北京现网推理集群` (`dbedee66-f03b-4554-a03f-c2c4723deeaf`) |
| 主题 | `infer-svc-log` (`79b65e74-4ec9-41bf-aa0a-005ad80d2d23`) |
| 存储 | 7 天 |
| 客户隔离维度 | `__TAG__.namespace`，如 `ns-svc-4pu8092b` |
| 集群规模 | 16 prefill pod + 4 decode pod（decode 侧另有 32 个 dp_rank） |

⚠️ **同名主题 `infer-svc-log` 在「HAI内部推理集群」「HAI测试推理集群」及一个同名日志集下还有 4 个，务必核对 TopicId。**

### 3.2 日志形态

日志是 SGLang 的 stderr/stdout 纯文本。**CLS 侧只有 `__CONTENT__` 一个大文本字段 + `__TAG__` 里的 K8s 元数据；所有指标埋在 Python repr 里，必须自己解析。**

两类记录，靠 `bootstrap_room` 关联：

```
Finish: obj=GenerateReqInput(rid='...', text='...', ...),
        out={'text':..., 'meta_info': {26 个指标}}
```
```
Receive OpenAI: obj={'messages': [...完整对话...], 'model': 'glm-5.2', 'tools': [...]}
```

| | Finish | Receive OpenAI |
|---|---|---|
| 占比 | ~2/3 | ~1/3 |
| 单条体量 | ~11 KB | **~286 KB**（max 1 MB） |
| 含对话正文 | 否（被中间截断） | **是，完整** |
| 时段覆盖 | 全天 | **仅部分时段**（实测存在整夜缺失） |

`meta_info` 的 26 个键中可用的主要有：`prompt_tokens`、`completion_tokens`、`cached_tokens`（**L1 唯一主信号**）、`reasoning_tokens`、`cached_tokens_details`、`total_retractions`、`queue_time`、`prefill_waiting_latency`、`prefill_launch_latency`、`e2e_latency`、`decode_throughput`、`dp_rank`、4 个时间戳、6 个 `spec_accept_*`、`finish_reason`、`weight_version`。

### 3.3 六个坑（接手前必读）

**① 健康检查占 62%，服务端过滤必须带通配符。**
`NOT __CONTENT__:"HEALTH_CHECK"` **完全不生效**（rid 形如 `HEALTH_CHECK_1788167986.861002`，被分词器切开）。必须写 `NOT __CONTENT__:"HEALTH_CHECK*"`。
> 我们最初就中过这招 —— 以为过滤生效了，实际 300 条里 186 条仍是健康检查，且没有立即发现。

**② 一个请求有两条 Finish，字段互补，且两侧 rid 不同。**

| 字段 | prefill 侧 | decode 侧 |
|---|---|---|
| `prefill_launch_delay` / `prefill_launch_latency` | 100% | 0% |
| `prefill_finished_ts` | 0% | 100% |
| `decode_throughput` / `spec_accept_*` | 0% | 100% |
| token 计数 / `queue_time` / `e2e_latency` / `bootstrap_room` | 100% | 100% |

**只能用 `bootstrap_room` 配对**。若不合并，会把互补字段误判为"50% 缺失率"。

**③ 约 17% 的日志行没有 `[时间]` 前缀**（采集时多行被拆），正则匹配头部时前缀必须可选，否则静默丢数据。

**④ `inference_time` 不可用。** 实测出现 −532818 和上千万秒的值，同记录 `e2e_latency` 正常。用 `e2e_latency`。`decode_throughput` 也有离群值（曾见 103308 tokens/s），需按上限过滤。

**⑤ CLS 的 `_time_ms` 只有秒级批次精度**（曾见 50 条日志共享 4 个时间值）。时序分析必须用 `meta_info.request_received_ts`。

**⑥ 无会话 ID。** `conversation_id`、`extra_key`、`routing_key`、`session_params`、`custom_labels`、`priority` 全部为 None（2260/2260 核对）。`rid` 每轮都变。

### 3.4 关于 block hash：确认不存在

逐一检索 `block_hash`、`page_id`、`kv_event`、`prefix_hit`、`radix`、`matched_tokens` —— **均无**。`remote_kv_token_ids` / `remote_kv_matched_tokens` 等字段存在但 **2260/2260 全为 None**（说明 P2P 未启用）。

**L1 侧实际只有 `cached_tokens` 一个标量。** 这直接导致原方案的"块级最长公共前缀"判据无输入数据（§9）。

**page_size 已确认 = 64**：2098 个 `cached_tokens` 样本 100% 被 64 整除，128 仅 50%、512 仅 12%，GCD=64。注意与我方离线口径（512，Mooncake）不同，跨口径块数结论不可直接比较。

### 3.5 取数方案与性能

**服务端聚合不可用**：该 topic 的**键值索引字段数为 0**（只有全文索引），`| select ... group by` 返回空列。只能拉原始记录后本地聚合。

优化过程：

| 方案 | 吞吐 | 7 天预估 |
|---|---|---|
| 单线程 page=1000 | 32 条/秒 | ~12 小时 |
| 6 并发 | 184 条/秒 | 2.1 小时 |
| **10 并发** | **211 条/秒** | **1.8 小时** |
| 16 并发 | 205 条/秒（无增益） | — |

最终 `fetch_finish_mt.py` 的设计：
- **只拉 Finish 不拉 Receive**：后者单条 286KB 且时段不全；热点预测不需要对话内容。**这一步让有效时间跨度从 3.3h 提升到 7 天**（详见 §10）。
- **10 并发 + 分片落盘 + 断点续传**：每片单独 `.done` 标记，中断重跑只补缺失。
- **超大片二分递归重试**：高峰时段 10 分钟片可能触发 `SearchResultTooLarge`（实测 1008 片中命中 1 片）。

**实际结果：7 天 1368391 条，41 分钟，0 缺失，0 坏行。**

### 3.6 合规处理

`Receive OpenAI` 含完整对话正文，实测可见客户源码路径（如 `/mnt/.../hat_internal/utils/const.py`）、内部系统名（Meegle/GTMP/JFrog/SaturnV）、业务文档内容。

我们的处理：
- 取数脚本在解析当场提取指纹与统计量后**立即丢弃正文，正文不落盘**（`fetch_dataset.py` 的 `parse_receive()`）。
- 建模主路径只用 Finish（纯元数据）。
- 调研中产生的含正文中间文件（322 MB）**已删除**。
- 落盘的 `finish_7d.jsonl`（957 MB）不含任何正文。

## 4. 发现一：亲和倾斜的量化

### 4.1 为什么不能用 Gini 绝对值（我们最初的错误）

最初结论："prefill 侧 token Gini 0.17~0.25，decode 侧仅 0.01~0.05，存在亲和倾斜。"

**这个论证站不住。** 7 天按小时统计暴露了原因 —— Gini 与负载强负相关：

| 时刻 | 请求/5min | Gini | 实际/随机 |
|---|---|---|---|
| 07:00 | 87 | **0.853** | 3.92 |
| 06:00 | 90 | 0.847 | 4.04 |
| 11:00 | 758 | 0.281 | 3.61 |
| 17:00 | 708 | **0.247** | 3.05 |

裸 Gini 在凌晨是白天的 3.4 倍，但**"实际/随机"倍数几乎不变**。低负载时少量请求随机落点就会推高 Gini —— 绝对值主要反映负载高低，不是亲和强度。

### 4.2 正确做法：对照随机分配基准

方法：把同一时间窗的实际请求数**均匀随机撒到 16 个 pod**，重采样 200 次得 Gini 分布，再看实际值的位置。

| 负载档 | 请求数/桶 | 实际 Gini | 随机基准 | 随机 P95 | 超出 P95 的桶占比 |
|---|---|---|---|---|---|
| 最低 20% | 98 | 0.722 | 0.265 | 0.331 | 89% |
| 次低 20% | 195 | 0.567 | 0.153 | 0.200 | 100% |
| 中间 20% | 406 | 0.262 | 0.106 | 0.139 | 100% |
| 次高 20% | 634 | 0.202 | 0.084 | 0.110 | 100% |
| 最高 20% | 849 | 0.154 | 0.073 | 0.095 | 95% |

请求数 ≥50 的 277 个桶：实际 0.371 vs 随机 0.121 = **3.07×**，99% 超出随机 P95。

### 4.3 7 天验证：结构性特征

**按天**（"实际 Gini / 随机基准"中位）：

| 08-28 | 08-29 | 08-30 | 08-31 | 09-01 | 09-02 | 09-03 |
|---|---|---|---|---|---|---|
| 3.97 | 3.89 | 4.03 | 3.53 | 3.65 | 3.31 | 3.61 |

**按小时**（7 天平均）：范围 3.05~4.45，最高在凌晨 0 点（4.45），最低在 17 点（3.05）。

**全期中位 3.73×，波动 3.31~4.46。** 跨工作日/周末、跨昼夜均稳定。

> **给工程实现的结论**：
> - P2P 触发阈值用 `Gini_actual / Gini_random`，**设在波动上界之上（建议 >4.5）**。
> - **不要用裸 Gini** —— 会在夜间误报（Gini 0.85 但只有 87 请求/5min，无实际压力）、白天漏报（Gini 0.25 但有 708 请求/5min）。正好与真实需求相反。

### 4.4 ⚠️ 纠正简版：7 天口径的 Gini 绝对值更低

7 天全量口径与小窗口的差异：

| 指标 | 小窗口（30min/1h） | **7 天** |
|---|---|---|
| prefill 请求数 Gini | 0.129 ~ 0.252 | **0.114** |
| prefill token Gini | 0.196 ~ 0.294 | **0.137** |
| prefill 未命中 token Gini | 0.306 | **0.090** |
| prefill 请求数 max/min | 3.3× ~ 28.8× | **2.51×** |
| decode 请求数 Gini | 0.010 ~ 0.055 | **0.008** |

**原因**：跨 7 天聚合后，各 pod 的短期热点相互抵消 —— 某 pod 这小时热、下小时冷，累计下来趋于平均。

**这不削弱结论，但改变了论证方式**：
- ❌ 不要说"prefill Gini 0.25 说明倾斜严重"（长期聚合只有 0.114）。
- ✅ 要说"**任一时刻**的倾斜是随机基准的 3.73 倍，且该倍数长期稳定"。
- **倾斜是瞬时现象，不是长期积累现象。** 这恰好符合 P2P 的用途：需要的是**实时**搬运决策，而非长期容量规划。

同理，**简版引用的"冷热 pod e2e 中位 34.43s vs 1.3s（25×）"是小窗口偶发值**。7 天口径下各 prefill pod 的 e2e_P50 范围仅 **0.78~1.07s（1.4×）**、P99 范围 18.08~24.33s（1.3×）。最热与最冷 pod（token 量差 2.9 倍）的 e2e_P50 几乎相同（1.04s vs 1.07s）。

→ **"冷 pod 更慢"在 pod 粒度上不成立**。缓存的价值要在**请求粒度**上看（§5.1），那里的证据强得多。

### 4.5 倾斜只在 prefill 侧

| | prefill（16 pod） | decode（4 pod） |
|---|---|---|
| 请求数 Gini | 0.114 | 0.008 |
| token Gini | 0.137 | 0.007 |
| 请求数 max/min | 2.51× | 1.04× |

decode 侧靠 32 个 `dp_rank` 打散，近乎完美均衡。原因合理：**只有 prefill 读 prefix cache、选点被 cache 命中驱动**。

→ 所有"pod 选点/搬运/均衡"的讨论限定在 prefill 侧。

### 4.6 模板族集中度（含一个统计陷阱）

按 system prompt 前 500 字符哈希划分"模板族"，看每族的请求是否扎堆在少数 pod：

| 族大小阈值 | 族数 | 最大 pod 占比中位 | 完全集中占比 |
|---|---|---|---|
| ≥2 请求 | 154 | 1.000 | 107/154 (69%) |
| ≥3 请求 | 99 | 1.000 | 57/99 (58%) |
| ≥5 请求 | 61 | 1.000 | 33/61 (54%) |
| **≥10 请求** | **24** | **0.962** | **11/24 (46%)** |
| ≥20 请求 | 9 | 0.538 | 2/9 (22%) |

⚠️ **统计陷阱**：prefill 侧 345 个族中过半只有 1~2 个请求，而"1 个请求的族"必然 100% 集中于单 pod —— 这是定义使然，不是亲和证据。
> 我们最初报告的"76% 模板族锁死单 pod"就是这个陷阱的产物（基于 ≥3 请求、仅 42 个族的小样本）。

**修正后的读法**：以 ≥10 请求为主口径 —— 最大 pod 占比中位仍达 **0.962**、46% 完全集中。**亲和真实存在，但比小样本口径显示的弱。** 报告集中度必须同时给出族大小阈值与族数。

## 5. 发现二：缓存的真实价值与排队现状

### 5.1 缓存价值随上下文规模急剧放大（最强的经济论证）

**方法**：控制 prompt 规模，比较高命中（>90%）与低命中（<50%）请求的 e2e。这样才能分离"缓存缺失"与"请求本身大"两个混淆因素。

| prompt 规模 | 低命中条数 | 低命中 P50 | 低命中 P90 | 高命中条数 | 高命中 P50 | 高命中 P90 | **P50 倍数** |
|---|---|---|---|---|---|---|---|
| 0~5k | 53409 | 0.42s | 2.78s | 10172 | 0.31s | 0.91s | 1.3× |
| 5k~20k | 11093 | 1.13s | 4.29s | 11190 | 0.45s | 1.32s | 2.5× |
| 20k~60k | 37908 | 3.13s | 7.39s | 137903 | 0.59s | 2.19s | **5.3×** |
| 60k~120k | 35075 | 7.14s | 12.78s | 175792 | 0.80s | 2.82s | **8.9×** |
| 120k~300k | 26149 | 13.62s | 22.51s | 139129 | 1.21s | 4.06s | **11.3×** |
| >300k | 49 | 31.58s | 42.60s | 160 | 2.08s | 8.94s | **15.2×** |

**该客户的 prompt 中位是 69831 token、P90 是 161788** —— 正落在缓存价值 **8.9~11.3 倍**的区间。

三个推论：

1. **丢失缓存的代价与上下文规模强相关**。对短 prompt（<5k）几乎无差异（1.3×），对长 prompt 则决定性（11~15×）。**P2P 搬运的收益模型必须按 prompt 规模分层**，不能用统一系数。
2. **这是比"冷 pod 更慢"更严谨的论证**（后者在 7 天 pod 粒度上不成立，§4.4）。
3. **搬运决策应优先服务大 prompt 请求** —— 它们的 `ΔTTFT_saved` 高一个量级，而搬运成本也高，但收益/成本比更好。

### 5.2 ⚠️ 纠正简版：排队确实存在，但只在高负载尾部

简版称"所有 pod 的 `queue_time` P99 恒为 0"—— **这是小窗口的采样假象**。7 天全量（689896 条 prefill）的真实分布：

| 分位 | queue_time |
|---|---|
| P50 | 0.0045s |
| P90 | 0.0191s |
| **P95** | **2.0424s** |
| **P99** | **11.0993s** |
| P99.9 | 22.7849s |
| max | 52.5185s |

> 小窗口 P99=0 是因为样本量不足以采到尾部。这是一个典型的分位数估计偏差。

**排队与负载强相关**：

| 负载档 | 请求/桶 | 排队>1s 的请求占比 |
|---|---|---|
| 最低 20% | 72 | 0.172% |
| 次低 20% | 144 | 0.221% |
| 中间 20% | 228 | 0.489% |
| 次高 20% | 441 | 2.376% |
| **最高 20%** | **827** | **10.644%** |

**按小时**：0.096%（05:00）~ 12.068%（17:00）。工作时段 10~17 点的排队比例是凌晨的 50~120 倍。

**修正后给合作方的判断**（比原判断更精确）：

- 排队**确实会发生**，且集中在高负载时段（>1s 占比可达 12%）。
- 但**中位与 P90 仍极低**（4.5ms / 19ms），即 **90% 以上的请求完全不排队**。
- → 若 `P2pCacheAwareSelector` 的"负载差达标"依赖排队指标（如平均或 P50 队列深度），**它在 97% 的时间不会触发**；只有在高负载时段的尾部才可能触发。
- → **建议双信号**：① 倾斜度 `Gini_actual/Gini_random`（实时、稳定、全时段可用）；② 高负载时段辅以排队尾部分位（P95/P99）而非中位。

### 5.3 命中率与请求规模的完整分布

| 指标 | P10 | P25 | 中位 | P75 | P90 | P99 | max |
|---|---|---|---|---|---|---|---|
| prefix 命中率 | 0.3% | 64.5% | **98.1%** | 99.4% | 99.7% | — | — |
| prompt_tokens | 7959 | — | **69831** | — | 161788 | 240857 | 490676 |

**命中率分布是强双峰的**：P10 仅 0.3%（全新会话首轮），P25 已达 64.5%，中位 98.1%。即**要么几乎全命中，要么几乎全不命中**。

→ 对 P2P 的含义：值得搬运的目标很好识别 —— 那些"本该高命中但当前低命中"的请求（跨 pod 漂移的会话中间轮）。

其他分布：
- `finish_reason`：length 52.7% / stop 47.3%
- 含投机解码指标：49.5%（即 decode 侧全部）

## 6. 发现三：负载画像与离线先验的差异

我们此前基于 Mooncake(3.9万)/BurstGPT(886万)/Azure/WildChat(83.8万会话) 的离线结论，在这个环境多数不适用：

| 维度 | 离线先验 | 本环境实测 | 差异影响 |
|---|---|---|---|
| prefix_hit_ratio | 编码 0.56 / 数学 0.58 / 闲聊 0.42 | **中位 98.1%** | 高一个量级。**"提高命中率"不是可行目标** |
| 会话画像 | 轻量问答 43% / 中等 39% / 深度多轮 18% | **agent 工具链为主**：97% 带 `tools`，messages 中 tool 角色占比中位 48% | 聚类比例不可套用，`cluster_w` 需重标定 |
| prompt 规模 | — | 中位 **69831**，P90 161788，max 490676 | 单请求 KV 体量巨大，搬运成本模型按此量级估 |
| 轮间隔 | （原假设分钟~小时） | **中位 10 秒**，P10 4s，74% <30s | **价值分缓存的陈旧容忍度差几个数量级** |
| 会话-pod 关系 | （原假设按 pod 分域） | 仅 **4%** 会话全程留在同 pod，**77%** 相邻轮换 pod | 按 pod 分域会把会话切碎 |
| L1 可用字段 | block hash 列表 | **仅 `cached_tokens` 标量** | 重建主判据必须换（§9） |

### 6.1 客户画像

从日志内容可判断（**仅用于理解负载特征，不作他用**）：客户端是 Claude Code 一类的 agent（可见 `system-reminder`、`Available agent types`、SessionStart hook），运行在 `glm-5.2` 上，业务是车机/自动驾驶研发（ADAS 域、车载 SoC、版本火车、Meegle 问题单）。

**这解释了所有异常指标**：agent 工具链自动循环 → 轮间隔 10 秒；每轮追加 tool_response → prompt 累积到 7 万~16 万 token；上下文只在末尾增长 → 命中率 98%。

### 6.2 时间结构（7 天数据独有）

**① 工作日日内曲线高度稳定，周末是另一种模式**

各天日内负载曲线（归一化）两两相关系数：

| 对比 | 相关系数中位 | 范围 |
|---|---|---|
| 工作日 × 工作日 | **0.914** | 0.84~0.99 |
| 含周末的配对 | 0.548 | 0.33~0.80 |

→ `hour` 特征**可用于外推**，但必须配 `dow` 或工作日/周末分模型。
> ⚠️ 若混算不区分，相关性只有 0.623，会误判为"周期不稳定、慎用 hour 特征"。实测 7 天模型的 Top 特征中 `min_of_day`/`hour`/`dow` 均进前 5，印证有效。

**② 周末负载仅工作日的 45%**：工作日 6 天日均 8.07e9 token，周末 2 天 3.61e9。
→ 预热/扩容阈值需按工作日/周末分别标定，否则周末大量误预热。

**③ 日内双峰**：10~11 点、14~17 点为高峰（~750 请求/5min），05~08 点为谷底（~90 请求/5min）。峰谷比约 **8.4×**。

## 7. 方案修正：从单边价值分到双边 gain

### 7.1 原方案的问题

我们原本的策略框架：

```
value(s) = P(continue) · (R̂ / mean_blocks) · cluster_w
```

**这是单边的** —— 单调偏好"更可能复用的会话"，即把请求往已有 cache 的 pod 上引。

**而这恰恰是合作方要解决的亲和倾斜的成因。沿用它会让问题更严重。**

### 7.2 修正后的双边形式

```
gain(r, s, t) = ΔTTFT_saved(r, t)               # 命中带来的省时（按 prompt 规模分层，§5.1）
              - λ_load · congestion(t)           # 目标 pod 拥挤度惩罚
              - λ_cost · transfer_cost(r, s, t)  # 搬运成本（KV 体量/带宽）
              + λ_future · P(continue|r) · R̂(r)  # 未来还会复用 → 更值得搬
              + λ_hot   · Ĥ(t)                   # 预期热度（预热用）

congestion(t) = w1 · norm(inflight_tokens(t))
              + w2 · norm(queue_p95(t))          # 用 P95 而非中位（§5.2）
              + w3 · (Gini_actual / Gini_random) # 倾斜度，相对随机基准（§4.3）
```

三点关键：

1. **`ΔTTFT_saved` 必须按 prompt 规模分层标定**：<5k 时约 1.3×，120k+ 时 11.3×（§5.1）。用统一系数会严重低估大请求的搬运收益。
2. **`congestion` 不能只看排队中位**（90% 请求不排队），也不能用裸 Gini（与负载负相关）。
3. **`P(continue)·R̂` 降为正向加权项之一** —— 它回答"值不值得搬"，不能单独决定"搬去哪"。

### 7.3 两级架构（据实测调整）

实测发现：**集群总负载可预测（R²=0.83），但它在 pod 间的分配近乎随机**（份额标签 R²=−1.19）。因为每轮请求本就随机落 pod。

| 层级 | 做什么 | 依据 |
|---|---|---|
| 第一级 | 预测**集群级**总负载与分位上界 → 决定是否预热、预热多少 | 模型（R²=0.827） |
| 第二级 | **pod 级选点** | 实时 congestion + 双边 gain，**不依赖预测** |
| 例外 | Top-K 少量预热（K≤10%） | pod 级模型（全档位优于基线） |
| 触发 | 当期实测 `Gini_actual/Gini_random > 4.5`；辅以预测告警（AUC 0.899） | §4.3、§8.2 |

### 7.4 延迟预算与在线架构

| 消费端 | 信号 | 频率 | 延迟预算 |
|---|---|---|---|
| `P2pCacheAwareSelector` | `gain(r,s,t)` 排序 | 候选匹配 | 亚毫秒 |
| `P2pNodeGate` | 高价值更长等待窗口 | 有候选 | 亚毫秒 |
| 预热前置 | 集群级 Ĥ 的 P90 上界超阈 | 分钟级 | 秒级 |
| 倾斜监控 | `Gini_actual/Gini_random` | 分钟级 | 秒级 |

分层惰性决策：
- **L0 规则闸门**（Gateway 内，0 ML）：不满足 P2P 条件 → 默认策略。
  > 实测支持把短期预测也放进 L0：≤15min 的预测用滑窗惯性即可（基线 R²≈0.50），模型仅 +0.05 增益。**模型只在 ≥30min 提前量上才有不可替代价值。**
- **L1 价值分缓存**：会话轮次边界重算，写 Gateway 本地只读注册表，决策时 O(1) 读。
  > ⚠️ 轮间隔中位仅 10 秒（§6），**陈旧上限应设为秒级（≤30s）**，而非原方案的 ">24h 或 >3 轮"。建议双触发：轮次边界 + 最小重算间隔（≥5s）取其晚者。
- **L2 天级重训 + shadow/灰度**。

关键路径增量目标 **p99 < 50µs**。**禁止把远端取 profile 或同步模型调用放进决策路径。**

## 9. 会话重建：方法与已知局限

### 9.1 为什么需要重建

任务 A（会话延续 P(continue)）与任务 B（复用潜力 R̂）都需要会话级标签。但日志无会话 ID（§3.3-⑥）。

### 9.2 方法：token 算术链

核心恒等式 —— 同会话相邻两轮，客户端重发累计历史：

```
cached_tokens(B) ≈ prompt_tokens(A) + completion_tokens(A)
```

实测满足率 **74%**（643 相邻轮对，容差 256 token）；`prompt_tokens` 单调不减 91%；messages 条数单调不减 94%。

判据：
```
ok = |cached_tokens(B) − ctx_A| ≤ tol
   & prompt_tokens(B) ≥ prompt_tokens(A) + min_add
   & cached_tokens(B) > T_template + margin
   & 0 < gap(A,B) ≤ gap_max
score = ok · exp(−gap/tau) · (1 + tpl_bonus if 同模板族) · (1 − d/tol)^0.5
```

参数（按实测校准，与原方案差异大）：`tol = 512~1024`（原建议 256 偏紧）、`min_add = 64`、**`tau ≈ 60s`、`gap_max ≈ 600s`**（原方案 1~4h / 24h，因轮间隔中位仅 10 秒）。`T_template ≈ 1793 token`（system 段中位，仅占中位 prompt 的 2.4%）。

### 9.3 质量评估（用内容指纹作准金标准）

原方案假设"完全无真值"。实测发现：**有 `Receive OpenAI` 的时段可用"首条 user 消息哈希"构造准金标准** —— 它把请求干净地分组（msgs 数单调递增可自证）。**该路径仅用于离线量化，不进生产**（用到内容，违反 L0+L1 约束）。

pairwise 同会话关系评估（3.3h 窗口、16635 请求、金标准 1032 会话）：

| 指标 | 值 |
|---|---|
| Precision | 0.508 |
| **Recall** | **0.067** |
| F1 | 0.118 |
| 重建会话数 / 真实 | 3112 / **1032**（过度切分 3×） |
| 链覆盖率 | 91.2% |
| 疑似漏链率 | 6.1% |

**tol 敏感性扫描**（说明 tol 是主导参数，tau/gap_max 影响很小）：

| tol | 最优 F1 | Precision | Recall |
|---|---|---|---|
| 64 | 0.029 | 0.291 | 0.015 |
| 256（原建议） | 0.169 | 0.581 | 0.099 |
| 512 | 0.233 | 0.567 | 0.146 |
| **1024** | **0.243** | 0.476 | 0.163 |

F1 在扫描边界仍单调上升，**应扫到 2048 以上确认拐点**（本次未做，是已知不足）。

### 9.4 成因与影响

**只能找回约 1/15 的同会话关系，找到的约一半是错的。** 成因：

1. 恒等式本身只有 74% 成立；
2. prefix cache 命中受**其他会话挤占/淘汰**影响，`cached_tokens` 并非纯由上一轮长度决定；
3. **跨 pod 漂移 77%**，同会话相邻轮落在不同 pod 的不同 cache 上，复用量被截断；
4. **不可限定 `pd_role=prefill` 做重建** —— 实测限定后 F1 从 0.146 跌至 0.067、疑似漏链率升至 76%（同一会话的轮次分散在 prefill/decode 各自日志中）。必须用合并后的请求级记录。

**影响**：任务 A/B 的标签噪声很大，效果预期应下调。**这是任务 C（热点预测，标签由时间窗聚合直接得到、不依赖重建）应优先的主要理由。**

### 9.5 突破口：block hash

块级前缀链能区分"真的复用了上一轮上下文"与"恰好长度接近"：
```
pre = 最长公共前缀块数(H_A, H_B)
ok  = (pre ≥ L_A − slack) & (L_B ≥ L_A + min_add) & (L_A > T_template)
```

Gateway 已在用 block hash 维护 HashTree（§2.1），**接入 KV Events 是突破 recall 天花板的主要希望**。

## 10. 方法论教训

### 10.1 小样本上的"否决"结论极不可靠

我们用 24h 数据（约 3000 面板样本）得出的多个结论，在 7 天数据（31472 样本）上**全部被推翻**：

| 24h 时的结论 | 7 天复测 | 修正 |
|---|---|---|
| 突发性特征**有害**（R² 0.228→0.029） | 精简 0.663 vs 全集 0.662（持平），大容量下 0.680 vs 0.685（略优） | **改为"无益也无害"**，此前劣化是过拟合假象 |
| `new_tokens` 标签**不可用**（R²=−2.81） | **R²=0.710** | **推翻**，"信噪比过低"判断错误 |
| 倾斜度二分类**不可预测**（AUC=0.343） | **AUC=0.899** | **推翻**，可作预警 |
| 集群级 R² 0.312 / pod 级 0.23 | **0.827 / 0.663** | 全面提升 |
| 分位数覆盖率 P90 76.6% | **87.1%** | 提升 |
| Top-K K=20% 输给基线（24% vs 30%） | **62.5% vs 53.5%** | 全档位领先 |

> **教训**：在小样本面板上判断"某特征是否有用""某目标是否可预测"极不可靠 —— **过拟合会把有效特征判成有害，噪声会把可预测目标判成不可预测**。
> **正确顺序是先扩样本，再调特征。** 凡"某方向无效"的结论，必须在样本量充足后复验。

### 10.2 分位数估计需要足够样本

简版称"`queue_time` P99 恒为 0"，7 天全量实测 P99 = 11.1 秒（§5.2）。小窗口的 P99 估计不可靠 —— **报告尾部分位时必须给样本量**。

### 10.3 聚合窗口会改变结论方向

同一指标在不同聚合窗口下差异显著（§4.4）：prefill token Gini 小窗口 0.196~0.294、7 天 0.137。原因是短期热点跨天相互抵消。
→ **倾斜是瞬时现象**。报告任何不均衡指标都必须说明聚合窗口。

### 10.4 比率型指标需要基准

裸 Gini 与负载强负相关（§4.1），单独使用会得出与事实相反的结论。**任何"不均衡度"指标都应对照同条件下的随机基准。**

### 10.5 控制混淆变量

"冷 pod 更慢"在 pod 粒度不成立（§4.4），但"低命中更慢"在控制 prompt 规模后极显著（§5.1，5.3~15.2×）。
→ **pod 是混淆变量**（热 pod 也接更多大请求）。要论证缓存价值，必须在请求粒度控制规模后比较。

### 12.3 术语

| 术语 | 含义 |
|---|---|
| L0 / L1 | L0=请求元信息（时间/长度/耗时/归属）；L1=Cache 元数据。**本环境 L1 实际只有 `cached_tokens`** |
| PD 分离 | prefill / decode 分池部署。两侧日志字段互补，按 `bootstrap_room` 配对 |
| 模板族 / 亲和族 | 同一 system prompt 前缀的请求集合。热点成因与选点依据 |
| `T_template` | 每域 system prompt 连续段长。本环境约 1793 token（占中位 prompt 2.4%） |
| `skew_ratio` | `Gini_actual / Gini_random`。**本报告推荐的倾斜口径**，实测稳定 3.73× |
| P(continue) / R̂ / Ĥ | 会话延续概率 / 复用潜力 / 预期热度（三个建模任务） |
| `gain(r,s,t)` | 双边价值：cache 收益 − 拥挤惩罚 − 搬运成本 + 未来复用 + 热度 |
| pinball loss | 分位数回归的损失口径 |
| conformal 校准 | 用留出集把预测分位的实际覆盖率修到目标值 |
