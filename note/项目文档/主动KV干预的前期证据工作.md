## 1. 我们的目标（一句话 + 三级阶梯）

合作方生产环境是**上游原版 sglang + mooncake**，目前唯一真实能力是**被动（request-driven）**：请求到达 → 其所在 pod 负载偏高 → 把该请求连同它的 KV 迁移/复制到另一 pod。粒度是"整个请求"，**没有**主动触发、没有无请求驱动的块级调度，也没有 KV Events / 块身份统计。

**公司为什么提出 P2P**：路由策略是 cache 亲和——把请求送到"能复用已有前缀缓存"的 pod。于是同一类会话（共享 system prompt / 前缀）会被持续送到最早缓存了该类前缀的 pod：缓存越全 → 命中率越高 → 越吸引后续请求，形成正反馈，结果同类会话都堆积在少数"前期"pod 上，造成 pod 间负载不均；而其他空闲 pod 因为没有缓存，每个请求都要全量 prefill。P2P 想打破的正是这个循环：把热点 KV 搬到空闲 pod，让请求可以路由过去而不损失缓存命中。§2 实测的"亲和倾斜 3.73×、同模板请求扎堆单 pod"就是这个背景的量化和验证。

我们想做的是**主动干预**，打算分三级推进：

```text
Level 0  现状：被动 request-driven（作为基线）
Level 1  shadow 决策：算出"本应执行的主动动作"但不执行、只落日志（行为零改变，先解决没有数据的问题）
Level 2  wedge：最小真实干预（只给预测热链预热空闲 pod），低风险、可回滚
Level 3  完整：触发后对每个 pod 上的 block/链做跨 pod 调度（放到最后）
```

你两块产出正好是 Level 1/2 的地基：T1 给借鉴清单与避坑，T2 给触发与调度选型的证据。

## 2. 公司生产数据分析结果（团队内部实测，供你设定仿真参数）

来源：内部对生产日志 7 天、137 万条请求（一家客户、16 prefill + 4 decode pod）的分析。内部报告原文请勿外传。

| 结论 | 数字 | 对你仿真器的含义 |
|---|---|---|
| 请求亲和倾斜稳定存在 | prefill 侧负载分配不均 = 随机分配的 **3.73×**（波动 3.31~4.46）；是瞬时现象、只在 prefill 侧 | 仿真要回答的核心问题之一：倾斜能否被主动干预缓解 |
| 命中/未命中代价随 prompt 规模急剧放大 | 低命中 vs 高命中 e2e 中位差：20k~60k=**5.3×**、60k~120k=**8.9×**、120k~300k=**11.3×**、>300k=**15.2×**（<5k 仅 1.3×） | **收益按 prompt 规模分桶**，用固定乘子表（§4.6） |
| 命中率强双峰 | 中位 **98.1%**，P10 仅 0.3%——要么几乎全命中、要么全新 | 倾斜成因是"某 pod 有该前缀缓存，别处没有" |
| 请求很大 | prompt 中位 69,831、P90 161,788、max 490,676 token | 单次搬运体量巨大，搬运成本不可忽略 |
| 负载可预测 | 集群级 60min R²=0.827、pod 级 R²=0.663；倾斜告警 AUC=0.899 | "预测热链再干预"在原理上可行 |
| workload 是 agent/工具链型 | 轮间隔中位 **10s**、77% 相邻轮换 pod、同模板请求扎堆（≥10 请求的模板族最大 pod 占 96.2%） | 这是"多轮、长上下文、高命中、快节奏"负载；公开数据里最接近的是 **Mooncake Tool/Agent trace** |
| 无会话、无块身份 | 无 session id；L1 只有 `cached_tokens` 标量；page_size=64 | → **决策单元定为"前缀链/块"，不依赖会话**（T3 按此实现） |

## 4. T3：多 Pod 回放仿真器

### 4.0 总目标
在公开 trace 上回答两个问题：
1. **headroom**：如果热点预测完美（Oracle），主动复制/搬移比"被动 request-driven 现状"多赚多少？（这是收益上限）
2. **选型**：用固定的简单预测（persistence / recency）能拿回 Oracle 的多少？触发阈值、动作粒度怎么选性价比最高？

**请按 workload 分开展示，不要合并结论**

### 4.1 仿真骨架

每个 pod = 一台带**本地前缀缓存（按块 hash 的前缀树）+ LRU 淘汰 + 容量（块数）**的 prefill 节点。请求按全局时间顺序到达，每个请求含 `{ts, 块序列}`（prompt 前缀 + completion 追加，沿用 `P_k⊂C_k` 口径）。

每请求处理顺序：路由选 pod → 查该 pod 最长缓存前缀（命中块数）→ 记录指标 → 写回 completion 块 → 执行当轮动作（见 §4.4/4.5）。

**路由策略（建议的固定枚举）**：
```text
R_AFF        亲和路由：选"当前缓存命中前缀最长"的 pod，平局取负载最小（用于复现现状的倾斜）
R_LEAST      纯最低负载路由（无缓存意识，作对照）
R_REQ_KV     被动 request-driven（Level 0 = 公司现状）：
             先按 R_AFF 选 pod；若该 pod 负载比 > θ（§4.6 参数表）→ 改投负载最小 pod，
             并把该请求所需 KV（前缀块）先复制过去再服务
```
- `R_REQ_KV` 是**主基线**，所有主动策略都要和它比净增益。
- 主动策略**不改路由规则**（仍是 R_AFF），它是靠"提前把热点链复制/搬到空闲 pod"来改变 R_AFF 的结果——多个 pod 都持有该前缀后，负载自然摊开。

### 4.3 决策单元：前缀链（chain）
块粒度太细、请求粒度太粗，统一用**前缀树节点 = 链**：
- 对全 trace 的请求块序列建一棵全局前缀树；每个节点 = 一条链（=某长度的公共前缀，被它的全部后代请求共享）。
- 链的命中语义 = 前缀缓存语义：到达某 pod 的请求只要块序列含该链前缀，就对该链计一次"命中复用"。
- 链体量 = 节点深度 × 块大小（token）；窗口内链热度 = 该窗口内经过该节点的请求数。

### 4.4 触发器策略（建议的固定枚举，建议逐一单独跑）
```text
T_NONE        不主动干预（配合 R_LEAST/R_AFF 作对照）
T_REQ         = R_REQ_KV 自身的触发（被动，主基线）
T_ORACLE      上界：已知未来 W 分钟内在"别的 pod"会被请求的热链，由 ground truth 直接算出（不使用任何学习）
T_PERSIST     预测：用最近 h 分钟热度 Top-K 链外推下一窗口（h、K 见 §4.6）
T_RECENCY     预测：链级 recency 打分（recency 加权历史命中），取分位 ≥ τ 的链（模仿 C11 的 reuse-history 特征，不训练模型）
```
- T_ORACLE 给**理论上限**，T_PERSIST / T_RECENCY 给**现实可做**的下限，两者之间的差就是预测提升空间。
- 如果你觉得有更值得试的触发方式，欢迎提出。

### 4.5 调度/落点策略（建议的固定枚举）

```text
目标 pod（全部策略共用）：负载最小，且空闲容量 ≥ 所需体量 × ρ（ρ=1.0）
目标容量不足：按固定 recency/freq 价值打分，LRU 驱逐目标 pod 上低价值链，逐出量 = 需让出的块数；仍不足则不动并记 fallback
动作：
  A_COPY   复制一份（源 pod 继续服务）   ← 默认
  A_MOVE   搬走并在源 pod 释放（作消融）
选哪些链：
  S_TRIGGER_ONLY   只对触发器给出的链集动作
  S_COST_AWARE     在 S_TRIGGER_ONLY 基础上，只对
      benefit(r) − λ_load·congestion(target) − λ_cost·transfer_cost > 0 的链动作
      benefit(r) = 该链未来 W 内预估命中次数 × ΔTTFT(prompt 规模桶)
      transfer_cost = 链 token 体量 / B
      （默认值见 §4.6；S_COST_AWARE 是主消融开关）
```

### 4.6 参数默认值
- 收益乘子 ΔTTFT（按命中前缀对应请求的 prompt 规模桶）：
  `<5k=1.3, 5-20k=2.5, 20-60k=5.3, 60-120k=8.9, 120-300k=11.3, >300k=15.2`
- 窗口：W ∈ {1, 5, 30} min
- 预测参数：T_PERSIST 的 h ∈ {1, 5} min、K ∈ {5, 10, 20}；T_RECENCY 分位 τ ∈ {0.8, 0.9}
- 负载比阈值 θ ∈ {1.5, 2, 3}
- pod 数 N ∈ {2, 4}；每 pod 容量按块数（沿用你阶段三口径：Qwen2.5-1.5B 448 KiB/块，8 GiB=18724 块；Mooncake 512-token 链按同口径换算）
- 带宽假设 B 取固定常量并在 README 写明（如 25 GB/s）；λ_load=0.5、λ_cost=0.1
- 前瞻 = 全 trace 已知（离线回放），时间顺序严格，禁泄漏

### 4.7 建议先跑的最小集（跑通后再扩展）
```text
主 workload（Mooncake toolagent 与 conversation 各一遍）：
  N=4，θ=2，W=5min
  行1  R_AFF                              （纯对照，描述现状倾斜）
  行2  R_REQ_KV                           （主基线 Level 0）
  行3  T_ORACLE + A_COPY + S_TRIGGER_ONLY （headroom 上界）
  行4  T_PERSIST(h=1,K=10) + A_COPY + S_TRIGGER_ONLY
  行5  T_PERSIST(h=5,K=10) + A_COPY + S_TRIGGER_ONLY
  行6  T_RECENCY(τ=0.9) + A_COPY + S_TRIGGER_ONLY
  行7  T_PERSIST(h=5,K=10) + A_COPY + S_COST_AWARE   （成本意识消融）
次 workload（WildChat，可选，作 conversation 佐证）
```

### 4.8 指标口径
每个 (workload × 策略 × 参数) 输出：
```text
Saved Prefill tokens / 等价 TTFT 增益（用 ΔTTFT 乘子折算，分桶展示）
请求级与 token 级命中率
负载倾斜度（Gini_actual / Gini_random，对照随机基准）
搬运次数与搬运体量（网络成本）
wasted-copy 占比：搬过去后 W 内未用到的链 token / 总搬移 token（误搬成本）
vs R_REQ_KV 的净增益（主指标）
```
汇总交付：一张 策略×参数 总表 + Oracle headroom（行3−行2）+ 曲线。**讨论基于系统净收益**，不只看预测指标。
