## 2. 多 pod 仿真器

模拟系统大致是：

```
                 Router

        ┌─────────┼─────────┐
        ↓         ↓         ↓
      Pod 1     Pod 2     Pod 3 ...
      Cache     Cache     Cache
```

每个 Pod 都有自己的：

- Prefix Cache
- 容量限制
- LRU
- 当前负载



按照真实公开的 trace 的时间顺序进行回放模拟

### 2.1 基础路由

#### 1. `R_AFF`：纯 cache affinity

```
哪个 Pod 当前 Prefix 命中最长
→ 请求就去哪个 Pod

平局时
→ 选负载最小 Pod
```

先复现问题，在公开数据集上验证 cache affinity 是否会造成负载不均衡



#### 2. `R_LEAST`：纯最低负载

选择当前负载最低的 pod

用于进行对照，说明不能为了负载均衡完全舍弃 cache



#### 3. `R_REQ_KV`：当前 request-driven P2P

主基线



### 2.2 主动触发策略

#### 4.  `T_ORACLE`：完美预测主动复制

假设知道未来 w 分钟

```
哪些 Prefix Chain 会被访问
访问多少次
什么时候被访问
```

提前将热链复制到低负载的 pod

在这种理想状态下，主动 KV Cache 相对于当前 request-driven P2P 最多还能赚多少



#### 5.  `T_PERSIST`：Persistence 热度外推

```
最近 h 分钟最热的 Top-K Prefix Chain
↓
认为未来 W 分钟仍然会热
↓
提前复制
```

简单的认为当前最热的 prefix 之后也会继续热下去

采用参数：

```
h ∈ {1, 5} min
K ∈ {5, 10, 20}
```



#### 6. `T_RECENCY`：最近复用优先

对于每条 prefix chain 计算分数，最近刚被访问过则分数更高

选择分数高于某个阈值的 chain 进行复制



### 2.3 做一个重要消融：Cost-Aware

将搬运成本和目标节点负载加入考虑，只有当收益存在的时候才进行搬运



### 2.4 COPY 和 MOVE 也要比较

默认主实验是：

```
A_COPY
```

即：

```
A 有 Prefix X
↓
复制到 B

最后：
A 有 X
B 也有 X
```

这是主方案。

同时也要测试 Move 策略，也就是 A 不保留 X



### 2.5 先跑最小实验

三个维度
$$
workload \times 策略 \times 参数
$$
先在每个
$$
workload \times 策略
$$
上跑通，然后再改参数



主 workload：

```
Mooncake Tool/Agent
Mooncake Conversation
```

分别跑，不合并。

固定：

```
N = 4 Pods
θ = 2
W = 5 min
```

然后跑 7 行：

| 实验 | 策略                                          |
| ---- | --------------------------------------------- |
| 1    | `R_AFF`                                       |
| 2    | `R_REQ_KV`                                    |
| 3    | `T_ORACLE + A_COPY + S_TRIGGER_ONLY`          |
| 4    | `T_PERSIST(h=1,K=10) + A_COPY`                |
| 5    | `T_PERSIST(h=5,K=10) + A_COPY`                |
| 6    | `T_RECENCY(τ=0.9) + A_COPY`                   |
| 7    | `T_PERSIST(h=5,K=10) + A_COPY + S_COST_AWARE` |



确认最小实验能够跑通之后再进行参数扫描



## 决策尺度：`prefix chain`

prefix chacin 是多个连续 block 构成的一条共享前缀路径

比如 3 个请求的前缀 block 是：

```
请求 A: B1 → B2 → B3 → B4
请求 B: B1 → B2 → B3 → B5
请求 C: B1 → B2 → B6
```

那么前缀树就是：

```
B1
└── B2
    ├── B3
    │   ├── B4
    │   └── B5
    └── B6
```

```
B1、B2
```

就是一条被 A、B、C 共享的 prefix chain



prefix chain 代表的就是一个有意义的连续公共上下文



按照整个请求来决策则粒度太粗了，不同的请求被当成了完全不同的对象，但其实真正有复用价值的是不同请求共享的前缀

按照block来请求则太细了，并且 cache 复用要求的是前缀连续命中，中间断开则后面的 block 也不能带来新的增益

所以按照 prefix chain 来进行决策在尺度和复用模式上都是比较好的
