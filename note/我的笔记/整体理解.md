# 主动 KV 干预

## 1. 项目背景

之前的项目研究的是：

```
用户 / 会话行为
        ↓
未来是否继续、多久继续
        ↓
未来 KV Cache 是否会复用
        ↓
决定哪些 Cache 值得保留
```

也就是人为会话的切换可能会带来 KV Cache 复用的损失，所以希望对会话行为进行分析，主要去预测 `是否继续会话`、`多久后继续会话`，从而指定 cache 管理的策略

现在面临的则是一个更实际的系统问题：

> KV Cache 负载不均衡

采用 `cache-aware / cache-affinity routing`，也就是优先将请求路由到有相关的 cache 的 pod 上

这样就会造成问题：

> 第一次某类请求发送到了 pod A，使得 pod A 有了某个 cache
>
> 接下来来了一些有相同前缀的请求，那么 pod A 有相关的 cache，就会优先将请求路由到 pod A
>
> 这样就可能会形成正循环：
>
> A 有 cache $\to$ 更多请求送到 A $\to$ A 有缓存了更多的 prefix $\to$ A 的 cache 命中的优势进一步扩大，更多的请求被路由到 A

于是就会导致负载不均衡，请求更倾向于路由到 A



所以此时就需要权衡两个方面：

1. cache 复用
2. 整个系统内 pod 之间的负载均衡



## 2. P2P KV transfer

目前已经有了一个 **P2P KV transfer 系统**

核心决策逻辑是：

```
Request
   ↓
Gateway
   ↓
找哪里 Cache 命中最多
   ↓
发现 Pod A 有最长 Prefix
   ↓
但 A 很忙
   ↓
发现 Pod B 比较空
   ↓
A → B 传 KV
   ↓
B 使用这些 KV 继续 Prefill
```

也就是路由逻辑会先选择有最长 prefix 缓存的 pod A

如果当前的 pod A 过热，就将 KV Cache transfer 到较为空闲的 pod B，将请求路由到 pod B

也就是主要依据：

```
当前 Cache 在哪里
+
当前 Pod 有多忙
```

来进行决策



> 合作方生产环境是**上游原版 sglang + mooncake**，目前唯一真实能力是**被动（request-driven）**：请求到达 → 其所在 pod 负载偏高 → 把该请求连同它的 KV 迁移/复制到另一 pod。粒度是"整个请求"，**没有**主动触发、没有无请求驱动的块级调度，也没有 KV Events / 块身份统计。

## 3. 现有的问题

现在已经解决了如何安全、快速地搬运 KV Cache

但是现在的决策系统还是 **request-driven**

也就是：

```
请求已经来了
      ↓
发现 Cache 在 A
      ↓
A 又很忙
      ↓
这时候才决定把 KV 搬到 B
```

已经有请求遇到负载不均的问题，才去进行解决

- 优点是请求已经来了，不会出现搬过去的 cache 没有用的情况
- 缺点是搬运本身也有延迟，请求来了再搬运会加大系统延迟

而现在想要做的是主动策略，也就是通过预测 cache 的访问情况，结合 pod 的热度提前将 prefix 复制到其他的 pod 中



## 4. 项目规划

```
Level 0
当前 request-driven P2P

        ↓

Level 1
Shadow
只计算“如果主动调度，我会搬什么”
不真正执行

        ↓

Level 2
Wedge
只提前复制少量预测热 Prefix

        ↓

Level 3
完整的主动 KV 跨 Pod 调度
```

- level 0 是项目的基线
- level 1 中进行决策的验证，实际执行 level 0 中的决策逻辑，同时 shadow 调度器记录主动调度策略的决策，这样就可以在不改变系统行为的基础上收集主动调度策略的决策结果，验证策略的正确性
- level 2 中开放部分测试，只允许主动策略去控制少量预测热的 prefix，初步验证效果
- level 3 才进行完整的调度
