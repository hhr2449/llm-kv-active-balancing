# P2P 已开启集群 `svc-rnwjq8pb` 对照分析

> **日期** 2026-09-04 · **数据** CLS `HAI北京现网推理集群 / infer-svc-log`
> **对照** `ns-svc-rnwjq8pb`（P2P 已开启）vs `ns-svc-4pu8092b`（未开启），同期 09-04 12:24~18:25
> **配套** `完整技术报告_KVCache亲和与负载倾斜.md`（主报告，基于 4pu8092b 7 天数据）

---

## 结论摘要

**⚠️ 先说结论的可信度**：这是**观察性对照，不是受控实验**。两集群的规模、配置、客户、负载都不同（下表），差异**不可直接归因于 P2P**。本文的价值主要在于：① 确认 P2P 集群的日志里有哪些新信号可用；② 记录一个影响主报告的数据事件；③ 说明为什么需要受控实验。

三个实质发现：

1. **P2P 集群有全新的可用信号**：`HICACHE_H2D_SUMMARY`（KV 搬运吞吐）、`Req Time Stats`（含 `transfer_duration`）、`mooncake` 与 `router` pod。这些在 4pu8092b 完全不存在 —— **主报告中"P2P 未启用、无法做效果对比"的判断可以更新为"有专用日志可用，但需要设计受控实验"**。
2. **`remote_kv_*` 字段不能用来判断 P2P 是否启用**：该集群 P2P 明确已开，但这些字段仍 0/156 全为 None。主报告用它推断"P2P 未启用"的做法不可靠（结论碰巧正确，依据错误）。
3. **发现一个影响主报告的数据事件**：`4pu8092b` 的 `queue_time` 在 **09-03 12 点左右从 100% 非零骤变为全部 0**，此后 30 小时保持 0。这是字段停止上报，不是排队消失。**主报告 §5.2 的排队分析只对 09-03 中午之前有效。**

## 2. P2P 专属日志（4pu8092b 完全没有）

### 2.1 `HICACHE_H2D_SUMMARY` —— KV 从 host 搬到 device

```
HICACHE_H2D_SUMMARY batch_id=50903 tp_rank=? queue_ops=1 batch_tokens=228672
  layers=78 pools=2 path=stable_group layout=layer_first backend=direct
  max_copy_bytes=67108864 complete_ms=239.16 tokens_per_ms=956.15
  mode=per-layer success=true
```

300 条抽样统计：

| 字段 | P50 | P90 | max |
|---|---|---|---|
| `batch_tokens` | 62272 | 155776 | 189760 |
| `complete_ms` | 150.4 | 385.4 | 1082.0 |
| `tokens_per_ms` | 493.5 | 1457.6 | 2193.8 |
| `layers` | 78 | 78 | 78 |

- `path=stable_group`、`mode=per-layer`、`backend=direct`、**`success=true` 100%**（300/300）
- **搬运吞吐中位 493 tokens/ms**（约 0.5M token/s）。以该客户 prompt 中位 74406 token 计，全量搬一次约需 **150ms**。
- 另有 `HICACHE_DIRECT_H2D_BOUNDED_START`（分段传输的起始记录，含 `items`/`item_bytes`/`segments`/`total_bytes`）。

> **这个吞吐数字对主报告 §7.2 的 `transfer_cost` 建模是直接输入** —— 此前只能估，现在有实测。

### 2.2 `Req Time Stats` —— 请求各阶段耗时（含 transfer）

```
Req Time Stats(rid=..., bootstrap_room=..., input len=104112, output len=59, type=decode):
  prealloc_queue_duration(3.97ms) = bootstrap(0.20ms) + alloc_wait(3.77ms);
  transfer_duration=1667.69ms; queue_duration=165152.14ms;
  forward_duration=3196.41ms, start=6988547.385
```

300 条抽样（`type` 分布：prefill 284 / decode 16）：

| 字段 | n | P50 | P90 | P99 | max |
|---|---|---|---|---|---|
| `input_len` | 300 | 34397 | 124384 | 194193 | 194193 |
| `bootstrap` (ms) | 300 | 4.4 | 512.8 | 15834.1 | 15838.8 |
| `alloc_wait` (ms) | 300 | 0.1 | 0.1 | 3.7 | 4.8 |
| **`transfer_duration`** (ms) | **16** | **1169.4** | 2576.6 | 4772.1 | 4772.1 |
| `queue_duration` (ms) | 300 | 5.9 | 33.5 | 50.9 | **170443.3** |
| `forward_duration` (ms) | 300 | 1516.6 | 3158.2 | 254864.1 | **1762056.2** |

**三点要注意**：
1. **`transfer_duration` 只有 16/300 条有值，且全部是 `type=decode`** —— 即 KV 传输只记在 decode 侧（PD 分离的 KV 交接），不是每个请求都有。P50 约 1.17 秒。
2. **`bootstrap` 的尾部极长**（P99 达 15.8 秒，P50 仅 4.4ms）—— 这个字段值得单独调查，可能是 P2P 协商开销。
3. **`queue_duration` 与 `forward_duration` 的 max 极端异常**（170 秒 / 1762 秒 = 29 分钟）。需确认是长输出请求的正常累计还是异常。

## 3. 同期对照（09-04 12:24~18:25，各 6 小时）

| 指标 | P2P 开启 | 未开启 | 说明 |
|---|---|---|---|
| prefill pod 数 | 4 | 16 | **配置差异，非 P2P 效果** |
| prefill 请求数 | 31989 | 39644 | |
| **请求数/pod** | **7997** | **2478** | P2P 集群单 pod 负载高 3.2 倍 |
| prompt 中位 | 74406 | 83524 | 相近 |
| prefill e2e P50 | 1.33s | 1.08s | |
| prefill e2e P90 | 5.30s | 3.78s | |
| prefill e2e P99 | 34.10s | 16.17s | |
| 命中率 P25 | 97.7% | 97.1% | 相近 |
| 命中率中位 | 99.4% | 99.2% | 相近 |
| 倾斜度（实际 Gini/随机） | **2.67×** | **3.49×** | 见下 |

### 3.1 e2e 更慢，但不能归因于 P2P

P2P 集群的 e2e 各分位都更慢（P50 +23%、P99 +111%）。**但这几乎肯定来自负载差异，不是 P2P 拖慢**：

- P2P 集群 **4 个 prefill pod 承担 31989 请求 = 7997 请求/pod**
- 对照组 **16 个 pod 承担 39644 请求 = 2478 请求/pod**
- **单 pod 负载高 3.2 倍**，e2e 变慢完全在预期内。

→ **要判断 P2P 对延迟的影响，必须控制单 pod 负载**，或在同一集群做开关对比。

### 3.2 倾斜度更低（2.67× vs 3.49×），但同样不可直接归因

按主报告的核心口径（实际 Gini / 同负载随机基准）：

| | P2P 开启 | 未开启 |
|---|---|---|
| 倾斜度中位 | **2.67×** | 3.49× |
| P25 ~ P75 | 1.96 ~ 3.48 | 3.12 ~ 4.05 |
| pod 数 | 4 | 16 |

**倾斜度低 24%，方向符合 P2P 的预期效果**（P2P 应当削平亲和倾斜）。但有一个强混淆因素：**pod 数不同**。4 个 pod 的 Gini 天然比 16 个 pod 更稳定（可选的"集中方式"更少），随机基准也随 pod 数变化。

→ **这个差异是"有希望但未证实"的信号**。需要在相同 pod 数下对比才能定论。

### 3.3 缓存价值：两集群一致

| prompt 区间 | P2P 开启 | 未开启 |
|---|---|---|
| 20k~60k | 3.3× | 3.9× |
| 60k~120k | 5.0× | 5.6× |
| 120k~300k | 5.8× | 8.2× |

主报告 §5.1 的核心结论（**缓存价值随上下文规模放大**）在两个集群都成立，倍数量级一致。这增强了该结论的可信度 —— 它不是单一集群的特性。

> 注：本窗口测得的倍数（3.3~8.2×）低于主报告 7 天口径（5.3~15.2×），因为 6 小时窗口的低命中样本少（P2P 集群 20k~60k 档只有 301 条），且缺少 >300k 档。

## 4. 发现的两个数据问题（影响主报告）

### 4.1 `remote_kv_*` 字段不能判断 P2P 是否启用

主报告多处写"`remote_kv_source_url` 等字段 2260/2260 全为 None，说明 P2P 未启用"。

**这个推断依据是错的**：`svc-rnwjq8pb` 的 P2P 明确已开启（有 mooncake pod、HICACHE 搬运日志），但它的 `remote_kv_*` 字段**同样 0/156 全为 None**。

→ 该字段族可能对应另一种远端 KV 拉取路径（非本地 P2P），或尚未接线。
→ **判断 P2P 是否启用应看：`mooncake`/`router` pod 是否存在、是否有 `HICACHE_*` 日志。**
→ 主报告关于 4pu8092b 未启用 P2P 的结论**碰巧是对的**（它确实没有 mooncake pod），但依据需要更换。

### 4.2 `4pu8092b` 的 `queue_time` 在 09-03 12 点后停止上报

按小时精查 `4pu8092b` 的 prefill `queue_time` 非零占比：

| 时刻 | n | 非零占比 | >1s 占比 |
|---|---|---|---|
| 09-03 10 时 | 7891 | 100.0% | 10.48% |
| 09-03 11 时 | 10435 | 100.0% | 13.43% |
| **09-03 12 时** | 245 | **38.0%** | 2.45% |
| **09-03 13 时** | 2890 | **0.0%** | 0.00% |
| 09-03 14~23 时 | 各数千 | **0.0%** | 0.00% |
| 09-04 全天 | 5385+ | **0.0%** | 0.00% |

**11 点还有 13.43% 的请求排队 >1s，13 点起完全归零并持续 30 小时。** 这种断崖式突变（而非渐变）说明是**字段停止上报或语义变更**，不是排队真的消失 —— 负载在 14~17 点仍处高峰（每小时 7000~8500 请求）。

**对主报告的影响**：
- §5.2 的排队分布（P95=2.04s、P99=11.10s、>1s 占 5.86%）是 **7 天全量**的，其中 09-03 中午前的数据贡献了全部非零值。**该结论只对 09-03 12 点之前有效。**
- §5.2 给合作方的建议"高负载时段辅以排队 P95/P99"**当前不可执行** —— 字段已无值。
- 主报告 §11.1 应新增一项待确认：**`queue_time` 为何在 09-03 停止上报？是否有替代字段？**
- 这也解释了为什么本次 6 小时对照中两集群的 queue 都是 0 —— 不是"都不排队"，而是**都没有数据**。

## 5. 建议的下一步

### 5.1 要得到 P2P 效果的可信结论，必须做受控实验

当前观察性对照的混淆因素太多（pod 数 4 vs 16、单 pod 负载差 3.2 倍、不同客户）。建议：

| 方案 | 做法 | 优点 |
|---|---|---|
| **A（首选）** | 在**同一集群**上做 P2P 开关的 A/B 或时间序列前后对比 | 消除配置与客户差异 |
| B | 找 pod 数与负载相近的两个集群对照 | 次优，仍有客户差异 |
| C | 在当前两集群上做**按单 pod 负载分层**的对比 | 可立即做，但只能部分控制 |

### 5.2 立即可做的事

1. **调查 `router` pod 的日志**（Rust `smg` 网关，带 `request_id`）—— 可能提供主报告 §9 缺失的会话关联键，若能拿到会话 ID，会话重建的 Recall 0.067 问题可直接解决。
2. **用 `HICACHE_H2D_SUMMARY` 的实测吞吐（493 tokens/ms 中位）标定主报告 §7.2 的 `transfer_cost`**。
3. **查清 `queue_time` 停止上报的原因**（§4.2），并寻找替代的排队观测字段。
4. **调查 `Req Time Stats` 的 `bootstrap` 尾部**（P99 15.8 秒 vs P50 4.4ms）—— 若是 P2P 协商开销，这是重要的成本项。

### 5.3 本次分析的局限

1. **观察性对照，非受控实验**（已反复强调）。
2 6 小时单窗口，未覆盖昼夜与工作日/周末变化。
3. P2P 集群的 Finish 日志只覆盖 4 个 prefill pod，replica pod（`-0-1` 等）的行为未知。
4. 未解析 `HICACHE_DIRECT_H2D_BOUNDED_START` 的完整字段族。
5. 未验证 `transfer_duration` 只在 decode 侧记录是否为设计如此。
